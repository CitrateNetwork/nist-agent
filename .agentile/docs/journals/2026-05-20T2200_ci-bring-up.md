# CI bring-up: secrets, first PR, watching it go green

> The federation-side and nist-agent-side scaffolding from S-1 and
> S-3 only fully exists when a PR actually goes green end-to-end on
> the CI runner — until then, the workflow YAML is a plan, not a
> system.

---

## Context

S-1 closed 2026-05-20 with the agentile structural docs in place.
S-3 closed 2026-05-20 (same day) with the Cargo workspace, the
first crate (`nist-agent-prelude`), the four cargo quality gates
(fmt, clippy, build, deny), and CI workflows (`ci.yml` and the
extended `ratchet-check.yml`). At this point local commands all
pass — but the workflows reference two repository secrets
(`AGENT_RUNTIME_DEPLOY_KEY` and `CHAIN_DEPLOY_KEY`) that nobody had
created yet. So the next operator step was: upload the secrets,
push a branch, watch the first PR's CI behavior, fix anything that
breaks.

This journal documents that bring-up.

## What happened

1. Verified the two readonly deploy keys exist locally at
   `~/.config/citrate-split-keys/{citrate-agent-runtime-fed-ro, citrate-chain-readonly}`.
2. Uploaded each as a GitHub repo secret on
   `github.com/CitrateNetwork/nist-agent` using
   `gh secret set ... < <key file>`.
3. Created branch `chore/ci-smoke-test` and authored this journal
   entry as a trivial-but-real change so the PR carries content
   instead of being empty.
4. Pushed, opened the PR, watched `ci.yml` and
   `ratchet-check.yml` run end-to-end on Actions.

## What this validates

- The agentile skeleton's `ratchet-check.yml` and the new `ci.yml`
  share an SSH-setup pattern. If either workflow has a typo or
  missing dependency, the first PR surfaces it.
- The two SSH host aliases (`github-citrate-agent-runtime` and
  `github-citrate-chain`) are configured by the workflow's
  `Configure SSH deploy keys` step. Cargo's git fetch must succeed
  through both aliases for the workspace to build.
- Cargo cache key (`Cargo.lock` hash) is honored across runs. A
  cold first run is the slow path; subsequent PRs reuse `~/.cargo`
  + `target/`.
